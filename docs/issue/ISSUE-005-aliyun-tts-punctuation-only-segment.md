# ISSUE-005：阿里云 TTS 遇到纯标点分段时中途合成失败

## 1. 缺陷信息

- 状态：已修复
- 优先级：P0（长脚本主合成链路确定性失败，并产生已完成的上游调用成本）
- 发现日期：2026-08-26
- 影响范围：`backend/app/tts/plan.py`、`backend/app/tts/routes.py`、`backend/tests/test_tts.py`
- 关联任务：T004（TTS 人声合成）

## 2. 用户现象

在 TTS 人声合成工作台中：

- 「应对亲密关系」脚本 v3 合成到一部分后失败。
- 页面提示：`阿里云 TTS 合成失败：Please ensure input text is valid.`
- 「缓解工作压力」脚本使用相同引擎、模型和音色可以成功。
- 浏览器控制台同时出现一条未包含请求 URL 的 404；现有证据不足以证明它与 TTS 主错误同源。

## 3. 定位证据

### 3.1 失败任务可稳定复现

失败脚本 artifact 为 `art_1787718369272_515894`，当前版本为 v3。两次运行都在完成第 32/162 个计划段后失败，错误和失败位置完全一致：

| run id | 文本长度 | 计划段 | 失败前进度 | 结果 |
| --- | ---: | ---: | ---: | --- |
| `run_1787748871963_03ab00` | 4167 | 162 | 32/162 | `Please ensure input text is valid.` |
| `run_1787748920426_891268` | 4167 | 162 | 32/162 | `Please ensure input text is valid.` |

前 32 个计划段包含 23 个阿里云语音请求和 9 个本地静音段；失败的第 33 个计划段是第 24 个阿里云语音请求。

### 3.2 失败段只有省略号

原始脚本包含：

```text
[吸气]……[呼气]……
```

计划器把 `[吸气]`、`[呼气]` 转成本地静音，却把标记之间的 `……` 生成为独立 speech 段。第 33 段实际发送文本只有两个 Unicode 省略号（`U+2026 U+2026`），不包含任何可发音文字，随后被阿里云拒绝。

该脚本 v1、v2、v3 均有两个同类纯省略号段；v3 中位于第 33、35 个计划段。

### 3.3 长度不是直接触发条件

| 对比项 | 应对亲密关系 v3 | 缓解工作压力 |
| --- | ---: | ---: |
| 文本长度 | 4167 | 1205 |
| 计划段总数 | 162 | 64 |
| 阿里云语音段 | 128 | 48 |
| 本地静音段 | 34 | 16 |
| 最长单次语音文本 | 82 | 49 |
| 纯标点语音段 | 2 | 0 |
| 运行结果 | 第 33 段失败 | 完成 |

系统按句拆分后逐段调用，并未把 4167 字整篇发送给 Provider。失败段只有 2 个字符；两次均在相同内容处失败。因此可排除整篇长度、单段长度、随机网络错误和累计段数限制是本次直接根因。

长脚本仍会放大影响：v3 当前需要 128 次 Provider 调用，执行时间、调用成本和遇到异常输入的概率均高于短脚本。

## 4. 根因

`build_plan()` 的 `push_speech()` 目前只过滤空白文本，没有判断分段是否包含可发音字符。因此纯标点、纯符号或不可见控制字符也可能进入 Provider 请求。

现有测试只覆盖呼吸标记旁边存在正常文字，没有覆盖 `[吸气]……[呼气]……` 这种真实冥想脚本写法。

Provider 异常在任务最外层统一转换为 `TTS_PROVIDER_ERROR`，未携带计划段号、语音请求序号或文本长度，导致前端只能显示笼统的上游错误。

## 5. 修复方案（已确认范围）

### 5.1 合成计划过滤与预检

1. 规范化待合成片段中的空白和不可见控制字符。
2. 仅当独立 speech 分段至少包含一个 Unicode 字母或数字时才进入计划；中文字符属于 Unicode Letter。
3. 跳过完全由 `……`、`——`、其他标点、符号或不可见字符组成的独立分段。
4. 正常句子中的逗号、句号、省略号等继续原样保留，避免改变朗读韵律。
5. 在任何 Provider 请求发出前验证完整计划，防止无效 speech 分段运行到中途才暴露。
6. 不修改原始脚本文本、artifact 或历史版本；过滤仅影响本次生成的 TTS 计划。

### 5.2 段级错误上下文

Provider 调用失败时，在不暴露完整脚本内容的前提下返回并持久化：

- 计划段序号/总段数；
- Provider 语音请求序号；
- 失败段文本长度；
- 原始上游安全错误信息。

前端已经直接展示 `run.failed.message`，后端补充上下文后即可显示更可操作的错误，无需复制脚本文本到前端。

### 5.3 本次不包含的优化

- 不合并相邻短句。
- 不调整 `MAX_SPEECH_CHARS`。
- 不修改情绪、语速、停顿和呼吸标记的时长语义。
- 不针对 404 猜测性改动；需取得具体请求 URL 后独立定位。

相邻短句合并可能减少长脚本 Provider 调用次数，但会改变韵律和错误恢复边界，应作为独立优化经试听验证后实施。

## 6. 测试方案

- 计划器：`[吸气]……[呼气]……` 只生成两个本地静音段，不生成纯省略号 speech。
- 计划器：纯标点、纯符号、零宽字符不生成 speech。
- 计划器：包含正常文字的标点和省略号保留。
- 计划预检：拒绝人工构造的无效 speech，且在 Provider 调用前完成。
- 错误上下文：模拟第 N 个 Provider 请求失败，验证任务错误包含段号、请求号和长度，不包含分段原文。
- 回归：fake TTS 完整链路、取消任务、MP3/WAV 及既有后端测试保持通过。

## 8. 实施记录

- 在 TTS 计划器新增 speech 文本规范化：控制字符与格式字符替换为空格，连续空白折叠。
- 使用 Unicode 字符类别判断可发音内容；独立分段至少包含一个 Letter 或 Number 才进入 speech 计划。
- 在长文本拆分前后都执行可发音判断，确保切分结果也不会产生纯标点 Provider 请求。
- 新增 `validate_plan()`，任务进入逐段循环前完成完整计划预检；无效计划返回 `TTS_TEXT_INVALID`。
- Provider 失败信息新增计划段号、总段数、TTS 请求序号和文本长度，不包含失败段原文；现有前端可直接展示增强后的 `run.failed.message`。
- 新增纯省略号、纯符号、不可见字符、正常句内标点、预检顺序和安全错误上下文测试。
- 使用真实数据库中的「应对亲密关系」v3 重建计划：总段数由 162 降至 160，speech 由 128 降至 126，silence 保持 34，纯标点 speech 为 0。
- 后端 TTS 专项测试：14 passed、1 skipped。
- 后端全量测试：115 passed、1 skipped；跳过项为环境条件控制的 FFmpeg MP3 测试。
- Python 语法编译与 `git diff --check` 通过。
